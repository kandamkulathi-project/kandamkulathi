# Current-primary knowledge foundation — KAN-86 / P1-MAT-003

**Candidate only; clinical, security and phase acceptance Pending.** Implements bounded R16/R17/C01/C03 foundations, not the complete chatbot or G1/G2 acceptance. The default Companion has no configured primary repository, authority, public seeds, provider or model. No fixtures are exposed through HTTP. Public knowledge requests are read-only; no public approval, withdrawal, indexing or intake endpoint is implemented.

## Owned boundaries

- `packages/contracts/src/knowledge.ts`: strict version-1 public knowledge/provenance, references, EN/ML/TA product manifest and typed decisions.
- `packages/domain/src/knowledge/`: pure lifecycle candidates, canonical hashes, trusted current-primary authorization, inventory reconciliation and derived public indexing projection.
- `apps/companion/src/knowledge/service.ts`: provider-independent injected service/HTTP adapter. `apps/companion/src/index.ts` deliberately supplies no dependencies.
- `packages/server/src/index.ts`: optional **third** argument registers routes before the generic unavailable fallback. The second argument remains reserved for the platform logging work; no platform driver, migration or logging code is copied.

## Content, provenance and transitions

Knowledge UUIDs use the shared internal `packages/contracts/src/identifiers.ts` helper: valid uppercase/mixed-case UUIDs normalize to **lowercase** during schema parsing. This applies to editor/approver, source/citation, product/entry/reference and audit evidence IDs, including trusted authority results **before identity comparisons**. Case aliases therefore identify the same principal and cannot become independent approvers; normalization grants no new permission and malformed authority results remain `FORBIDDEN`. Content hashing parses first, so semantic UUID aliases produce the same canonical content hash. Primary inputs are parsed before approval checks and repository lookups/final fences receive canonical UUIDs. Adapters must use the same canonical identities for persistence/CAS/fence comparisons; PostgreSQL UUID equality must not be replaced with case-sensitive raw text equality. SHA-256 values remain strict 64-character lowercase hexadecimal (uppercase hash strings are rejected), and exact approved text, citation titles and URLs are never case-normalized. Existing records must validate against their supplied hash after canonical parsing; historical hashes computed over noncanonical UUID spellings are not silently rewritten or reapproved and fail closed pending controlled validation/re-ingestion.

Mandatory safety hint selection in authorization and coverage uses the same validated canonical UUID comparison as other lookups, including alphabetic mixed-case primary IDs. Selecting an ID hint never authorizes the record: full public schema, canonical content hash, approval, scope/revision and final primary fences still apply to the original unmodified input. Historical hashes over noncanonical UUID spellings remain invalid; no lookup or validator rewrites those hashes.

The content hash is SHA-256 of an explicit ordered version-1 field tuple, including identity/revision/previous hash, visibility/scope/product/language/kind, exact title/text, editor, ordered source IDs/revisions/byte hashes/public URLs, and exact ordered citations. JSON object insertion order is irrelevant. Whitespace, language, source hash and citation changes alter the hash. No trimming, translation or generated paraphrase modifies approved text. A future canonicalization change requires a new schema version and reapproval, not silent hash rewriting.

Public provenance accepts only explicit public sources and HTTPS reference URLs without credentials/query/fragment. The domain never fetches those URLs. `draftKnowledge` checks supplied local source bytes against each source hash. This is integrity, **not** proof of a public URL's ownership, source correctness or medical approval: ingestion must classify sources, establish rights/publication approval and verify immutable source-object bytes. Primary reads recompute the content hash; the trusted authority verifies the approval and its bound evidence/version against actual current grants. Clinical/private records must never be supplied to this public ingestion boundary.

Transitions return immutable **candidates**, not persisted successes:

1. New entry → draft revision 1, null previous hash, currently authorized editor.
2. Existing entry → a new draft at exactly previous revision + 1, same entry ID, exact previous content hash and a currently authorized editor. An approved revision is not edited in place.
3. Draft → approved at the same revision/hash only by a **different**, independently authorized approver. Approval binds the exact content hash, named public reviewer, authority version, timestamp and evidence ID. The adapter must require current company physician qualification for medical content and the actual reviewed scope matrix; the engine does not invent those grants.
4. Approved → withdrawn preserves the approved text/hash/approval and records the authorized withdrawal actor/time/evidence. Withdrawal cannot predate approval. Withdrawn → approved at the same revision is forbidden; a fresh chained draft and independent approval are required.

The candidate's `expected` entry/revision/hash/state is a compare-and-swap precondition. A platform persistence adapter must revalidate the actor/grants and current row, enforce no duplicate entry/revision, atomically persist the transition with immutable audit and relevant outbox/index invalidations, and reject stale concurrent candidates. A null expectation requires the entry not to exist. This code has **no production in-memory store, database driver, migrations, transaction implementation or durability claim**. It does not compete with platform PR3.

## Read authorization and concurrency

`authorizePublicKnowledge` accepts a strict public-product request with one to twenty bounded candidate references. Exact/alias/keyword/vector references have identical trust: they are lookup hints, never approval evidence. Candidate text, role, approval, intake and generated-text fields are rejected.

Within `TrustedKnowledgeRepository.withCurrentRead`, the engine:

1. Loads the current published product and its primary EN/ML/TA manifest.
2. Loads each candidate's **current primary entry**, not its requested historical revision. Requires current approved state, valid content hash/provenance, current independently verified approver authority, exact manifest reference, product, language and catalogue scope. One invalid candidate blocks the entire answer; no best-effort partial medical answer is returned.
3. Calls `loadMandatoryBlocks(productId, language)` **independently** of candidate retrieval/ranking. All dosage/contraindication/safety blocks must be present, independently approved, hash/revision/manifest matching and in the same product/language/scope. No EN fallback supplies missing ML/TA safety. These are required content categories, not invented dosages or decision rules.
4. Calls `confirmCurrent` on the full product manifest and exact approved records, including approval metadata. A real adapter must atomically fence publication/manifest revisions, entry current revisions/hashes/lifecycle/approval, and current reviewer authority versions/revocations. A stale snapshot comparison, vector metadata comparison, or `return true` is **not** sufficient. Use the platform's reviewed primary transaction/locking path and prove it on real PostgreSQL, including rollback, lock conflict and RLS behavior. No provider call may hold database locks.
5. Returns copied, recursively frozen exact approved blocks/citations and allowlisted named public approval metadata (reviewer ID/name, approval time and content hash; no internal authority version, audit evidence or editor identity). There is no free-form generated-text parameter or merge operation. Any future nonclinical generation must use a separate, reviewed presentation slot and may never replace, reword or interleave into the medical blocks.

The final successful fence is the decision's linearization boundary. A withdrawal/publication/authority change **before** it must block; a change **after** it cannot retroactively retract already transmitted text. Every new request must reauthorize; responses use `Cache-Control: no-store`. No cache, previously ready result, index projection or historical revision is permission to render a later answer. Product/authority versions must increase on relevant changes; immutable revisions and forbidden same-revision reapproval prevent an ABA withdrawal bypass. Index deletion/freshness measurements remain required, even though primary checks deny stale hits immediately at the read boundary.

Typed `blocked` outcomes contain only a reason, never partial medical content. Missing configuration or primary/authority failure yields `not-ready`. Exception details and raw prompts are not exposed/logged here. No company-approved handoff wording is fabricated.

## Coverage and public indexing

`reconcilePublishedKnowledge` consumes the repository's **complete** current published inventory, not a user-selected sample. It emits one row per product × EN/ML/TA × monograph/dosage/contraindication/safety, with exact product revision and explicit missing-reference, missing-primary, withdrawn, stale, unauthorized, invalid-provenance or wrong-scope gaps. It counts expected/covered/gap slots and fences both product state and full inventory membership (including concurrent new publications). Malformed/duplicate/unpublished inventory rows fail closed rather than silently shrinking the denominator. Empty inventory truthfully reports zero; it is not proof that the actual catalogue has no products.

`projectPublicKnowledge` loads current primary state, verifies approval/authority/hash, checks published product and manifest membership where applicable, and fences current state. It allowlists public content/source hashes/citations into an immutable **derived** projection. It emits no editor ID, approval evidence or private records, makes no embedding/provider request, and cannot authorize a response. Institution-scope physician-profile/department/treatment/FAQ/policy/reference kinds are represented; actual approved sources remain unavailable. Consumption still needs current primary lookup. No provider SLA, company freshness deadline or measured coverage is invented.

## Service contract and unavailable features

- `POST /v1/knowledge/public-product`: JSON public-product request; 200 for an authorized injected result, 400 invalid JSON/input, 409 blocked current-state decision, 503 not-ready, 413 inherited body limit. The default runtime always returns `not-ready / NOT_CONFIGURED` for JSON input, regardless of fabricated role/session headers. The read-only POST has no business side effect; it does not broaden existing cross-origin permissions.
- `POST /v1/knowledge/personalized`: always 503 `blocked / PERSONALIZED_POLICY_UNAVAILABLE`; it does not parse or require intake. Ordinary public browsing is independent of intake/session.
- No medical/red-flag classifier, age/pregnancy/child threshold, diagnosis, personalized recommendation, dosage calculation, no-sale routing policy, tools/confirmations, escalation queue, rate-limit/model lease, streaming or provider is supplied. Those require reviewed policy, trusted identity/consent and separate implementations. Public catalogue reading is not authorization to buy a consult-only product.
