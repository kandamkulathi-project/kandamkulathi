## Proposed Core and Companion API handoff — review Pending

Use the existing minimum, bounded, session-bound, no-store adapter. Mutations require the exact approved Origin/CSRF policy plus durable server idempotency; never trust an author, role, approval or scope supplied by the UI. Return current data only after a real authorized operation. Deny unknown/expired sessions and cross-company/cross-user references. Recheck authorization and revision atomically at the write, not only at an earlier read.

| Service / route | Proposed contract / owner obligation |
|---|---|
| Both: `GET /v1/security/context` | Subject/session/expiry binding. Companion is a separate origin/Worker, so do not assume Core cookies or cross-origin native tokens automatically authorize it. Mathew must approve cookie audience/domain/SameSite/CSRF and native token audiences before enabling either. |
| Core: `GET /v1/knowledge/drafts/:id` | Authorized current draft, author ID, revision, state, structured document and server-derived edit/approve/withdraw permissions. No patient records or secret storage URLs. |
| Core: `POST /v1/knowledge/drafts` | `{id, expectedRevision, document}` plus operation key. Server supplies author, revision/state and provenance checks. Validate required source type/licensing, scope and medical safety; source URL validation in the client is not SSRF protection. Do not make arbitrary HTTP fetches; use an approved ingestion allowlist with DNS/redirect/private-network controls. |
| Core: `POST /v1/knowledge/drafts/:id/request_review` | `{expectedRevision}`. Save and review are separate. Preserve immutable version/audit history and exact source/translation checksums. |
| Core: `POST /v1/knowledge/drafts/:id/approve` | Independently authorized physician, not this revision's author/editor. Atomically verify current grants, version, source, company clinical and translation rules. Approval/publication/index consistency needs backend proof. |
| Core: `POST /v1/knowledge/drafts/:id/withdraw` | Authorized current approved revision, expected revision and auditable reason under the final reviewed policy. Remove from all retrieval channels, cached responses and pending work with measured freshness. |
| Companion: `POST /v1/chat/replies` | `{operationId, locale, message}` → reference-only answer or fixed `handoff_required`, `intake_required`, `action_required`, `unavailable` envelope. No executable tool payload, model-generated clinical prose, patient instructions-as-policy or synthetic provider success. Rate limits, consent, red-flag routing, public-only RAG, model budget and cross-user tool authorization remain Mathew's responsibility. |
| Companion: `GET /v1/knowledge/approved/:id` | Latest entry, not a caller-selected historical approved revision. Includes current state, approvedBy identity, reviewUntil and immutable document/version. Require current independent physician approval for medical entries and expose only approved public knowledge. |
| Companion: `POST /v1/support/handoffs` | Explicit locale-scoped customer request → persisted queued ID. Durable queue/deduplication, actual assignments, summaries, WhatsApp acknowledgement and resolution remain backend/domain work. |

The five-second request bound, 64-KiB response limit and 64-unresolved-operation in-memory key budget are reused from P1-DEV-003 for inferred consent/payment/draft action identities. A validated response or definitive rejection retires those inferred keys; only ambiguous retries of unchanged input retain them within that client lifetime. Chat and handoff already receive an explicit caller-owned UUID: it is sent unchanged as `Idempotency-Key` on every retry/replay of that action, without allocating a second hidden identity. A new explicit action needs a new UUID. This retains P1-DEV-004's duplicate protection while preserving PR #5's consent/payment fixes. Refreshing is not durable deduplication. Unknown mutation outcomes require authoritative lookup/reconciliation. Mathew must supply a reviewed operation-status endpoint before real draft/handoff recovery is accepted; never generate a replacement operation to hide uncertainty. The backend must bind every identity to its authenticated actor, route and payload and reject mismatched reuse.

## Local security findings and limits

- The review found and fixed source expiry during parallel retrieval, overlapping source refresh, unsaved-editor review and pagehide session suspension. The additional same-turn session-response/pagehide browser regression reproduced stale access restoration before a synchronous generation fence was added; cancellation alone was insufficient. Permanent unit/browser regressions cover the applicable boundaries. No new dependency or agreed stack change was needed.
- Existing local exact-origin CORS, no-store errors/request IDs, bounded client errors and session/CSRF/lifecycle guards were retained. Server errors are not rendered as raw HTML or logged with request payloads. Actual authenticated cookies/MFA/session revocation, private files and backend authorization cannot be validated against a 503 scaffold.
- The CSP added here restricts framing/base/object embedding. It is **not a complete script/connect-source policy**. Before production configure reviewed host headers, TLS/HSTS and explicit script/connect/media allowlists compatible with actual Razorpay and video flows; exercise them against the real providers. No claim of comprehensive XSS protection is made.
- The artifact audit detects configured markers and Gitleaks patterns, including ASCII strings in Hermes exports. It is not a general private-health-data detector or exhaustive bytecode/data-flow analysis. Do not place private data in bundles even if a scanner passes. Native installed-binary inspection and safe telemetry review remain required.
- Existing raw dependency advisories for the two proven source-patched packages remain visible. The installed-source exploit checks, all-severity audit policy, SAST, secret and official runtime checks remain mandatory; no finding is suppressed here.
- Real PostgreSQL/RLS/queues/outbox, observability alerts, 30-day availability SLI, load/soak, backup/restore and versioned deployment/rollback proof remain with the P1-DEV-001/Mathew integration. This branch does not duplicate or certify that separate PR. In particular, locally green source checks cannot establish 1,000-user capacity or production readiness.
